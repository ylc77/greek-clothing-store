# 服装店项目正式商用补全路线图

本文档用于说明当前 v1.0 商用演示版已经具备的能力、正式商用前仍需补齐的边界，以及后续面向希腊服装店客户时的开发优先级。

## 1. 当前 v1.0 商用演示版已完成功能

当前版本已经可以作为服装店数字化系统的商用演示版，覆盖从商品展示、后台管理、库存到 POS 收银的完整演示链路。

已完成能力：

- 官网展示
  - 首页
  - 分类页
  - 商品详情页
  - 联系方式、WhatsApp、Instagram、Skroutz 入口
  - 多语言前台展示

- 商品后台
  - 商品新增、编辑、上下架
  - 商品图片上传
  - 商品多图管理
  - 分类管理
  - CSV 导入
  - Skroutz Feed 配置和检查

- ERP 库存
  - product variants
  - 尺码库存
  - ERP 库存余额
  - 库存流水
  - 手动库存调整
  - 低库存提醒
  - ERP 与旧商品库存字段对账

- POS 收银
  - 后台 POS 收银 tab
  - 商品搜索 / barcode / variant_sku 搜索
  - 购物车
  - dryRun 预检
  - checkout
  - RPC transaction 路径已在 production 启用

- 订单历史
  - POS 订单列表
  - 订单详情
  - payment 信息
  - 对应库存流水

- 作废订单
  - completed 订单可作废
  - 作废后库存加回
  - 写入 return / pos_void 库存流水
  - 幂等保护，避免重复加库存

- 小票预览
  - 浏览器小票预览
  - 58mm / 80mm 纸宽
  - window.print 浏览器打印
  - 明确标注不是正式税务发票

- Barcode / 标签打印
  - variant barcode API
  - barcode = variant_sku 的第一版策略
  - 标签打印 UI
  - Code 128 条码图
  - 40x30 / 50x30 / 60x40 标签尺寸

- Skroutz Feed
  - /feed.xml
  - 商品字段检查
  - 图片、库存、分类、价格等 feed 必要字段输出

## 2. 当前版本边界

当前 v1.0 是商用演示版 / 内部试运行版，还不是完整正式合规商用版。

当前边界：

- 小票不是正式税务发票。
- 未接 AADE myDATA。
- 未接电子发票服务商。
- 未接银行 POS / Viva / myPOS API。
- 未做员工权限，目前后台仍以管理密码为主。
- 未做复杂退款，例如部分退款、部分退货、贷项凭证等。
- 未做采购入库、供应商、进货成本。
- 未完成真实硬件验收：
  - 真实扫码枪
  - 真实标签打印机
  - 真实小票打印机
  - 真实钱箱 / 切纸 / 开钱箱测试

## 3. 正式商用前必须补的功能

正式给客户部署或用于真实店铺经营前，建议优先补齐以下通用能力。

### 员工权限

需要从单一后台密码升级为正式登录和角色权限。

建议角色：

- 店主 / 管理员
- 店员 / 收银员
- 库存管理员
- 只读查看

权限边界建议：

- 店员可以 POS 收银、查订单、快速售出。
- 店员不能删除商品、修改系统设置、导出敏感数据。
- 库存管理员可以调整库存和打印标签。
- 店主可以查看报表、配置 feed、修改分类和设置。

### 备份策略

正式商用不能只依赖手动备份。

建议：

- 升级 Supabase 计划或制定定期导出策略。
- 重要 migration 前必须手动备份。
- POS、库存、订单、发票相关表必须可恢复。
- 备份文件不得提交到 GitHub。

### 错误监控

建议补齐：

- Vercel runtime error 监控
- POS checkout / void 错误日志
- ERP 对账异常提醒
- myDATA / 发票上传失败提醒
- 每日健康检查流程

### 退款 / 退货

当前已有 void 作废，但正式经营还需要：

- 全单退款
- 部分退款
- 是否退回库存
- 退款原因
- 操作人记录
- 与支付渠道和发票状态的对应关系

### POS 日报

正式店铺每天需要对账。

建议报表：

- 今日销售额
- 现金 / 刷卡 / other 支付统计
- 订单数量
- 作废订单数量
- 热卖商品
- 低库存商品
- 销售明细导出

### 真实硬件验收

上线前必须测试：

- 扫码枪能否正确输入 barcode / variant_sku。
- 标签打印机打印的条码是否清晰可扫。
- 小票打印机 58mm / 80mm 打印效果是否稳定。
- 是否有空白页、偏移、乱码、换行问题。
- 希腊语、中文、欧元符号是否能正常打印。

### myDATA / 电子发票服务商调研

正式税务发票建议不要盲接，需要先确认：

- 客户会计师要求
- 客户 VAT 类型
- 使用哪家电子发票服务商
- 是否需要零售收据、发票、贷项凭证
- 作废和退款如何在发票系统中处理

### POS 机联动调研

线下刷卡需要确认：

- 客户使用 Viva、myPOS，还是银行 POS。
- 是否有 API。
- 是否支持 POS interconnection。
- 刷卡成功后如何回传 payment reference。
- 刷卡失败、取消、超时如何处理。

## 4. 希腊合规调研清单

正式商用前，需要和会计师、电子发票服务商、支付服务商分别确认。

### AADE myDATA

需要确认：

- 是否由系统直连 myDATA。
- 是否通过认证电子发票服务商间接上传。
- 需要上传哪些发票类型。
- 零售销售如何上报。
- 作废、退款、贷项凭证如何处理。
- MARK、UID、QR URL 如何保存。

### 电子发票服务商

候选方向：

- Epsilon Net
- SoftOne
- Oxygen
- Viva 相关电子发票方案
- 其他希腊本地认证服务商

需要向服务商确认：

- API 文档
- 测试环境
- 认证方式
- 发票创建接口
- 作废 / 取消接口
- 退款 / 贷项凭证接口
- QR / MARK 返回字段
- API 费用
- 是否支持 POS 销售场景

### POS interconnection

需要确认：

- 自研 POS 是否需要和刷卡终端互联。
- 哪些交易必须触发 POS 机。
- 现金交易是否也需要特殊处理。
- ERP / POS 系统需要保存哪些 payment reference。
- 失败交易如何回滚。

### 会计师确认问题

建议问会计师：

- 店铺应该开 Retail Receipt 还是 Invoice。
- 服装商品 VAT 税率。
- 线上订单和线下 POS 是否使用同一发票流程。
- Skroutz 订单如何开票。
- 退货和换货如何处理税务。
- 是否允许先用服务商后台人工开票，系统后续再 API 对接。

### Viva / myPOS / 银行 POS 问题

需要确认：

- 是否提供 API。
- 是否支持远程发起支付。
- 是否支持 payment intent / terminal payment。
- 是否能回传交易状态。
- 是否支持测试环境。
- 是否满足希腊 POS interconnection 要求。

## 5. 推荐开发顺序

### 第一阶段：稳定和权限

目标：让系统更像正式后台，而不是单人演示工具。

建议开发：

- Supabase Auth 或等价登录方案
- 员工角色和权限
- 操作日志增强
- 后台敏感操作保护
- 备份和恢复流程文档

### 第二阶段：报表和退款退货

目标：满足真实店铺每天收银和对账。

建议开发：

- POS 日报
- 销售统计
- 支付方式统计
- 全单退款
- 部分退货设计
- 退款原因和操作人记录

### 第三阶段：硬件验收

目标：确认系统能在真实店铺设备上落地。

建议测试：

- 扫码枪
- 标签打印机
- 小票打印机
- 58mm / 80mm 小票
- 40x30 / 50x30 / 60x40 标签
- 浏览器打印效果

如果浏览器打印不稳定，再考虑：

- 本地打印桥
- ESC/POS
- 切纸
- 开钱箱

### 第四阶段：myDATA / 发票服务商调研

目标：确定合规方案，而不是盲目开发。

建议动作：

- 询问会计师
- 选择服务商
- 获取 API 文档
- 申请测试环境
- 设计 invoice_documents / provider_api_logs
- 明确作废和退款流程

### 第五阶段：正式发票和支付联动

目标：真正进入正式商用闭环。

建议开发：

- 发票服务商 API 对接
- MARK / QR 保存
- 税务小票打印模板
- POS 刷卡终端联动
- 线上支付联动
- 发票失败重试和人工处理队列

## 6. 对客户展示时的说法

### 可以说什么

可以对客户说：

- 这是一套面向希腊服装店的自研官网 + ERP + POS 商用演示系统。
- 已经支持商品展示、后台商品管理、尺码库存、POS 收银、订单历史、作废订单、标签打印和 Skroutz Feed。
- 当前版本适合演示、内部试运行和业务流程确认。
- 系统已经预留了 myDATA、电子发票、支付终端和正式权限体系的扩展方向。
- 正式上线前会根据客户的会计师、发票服务商和 POS 机品牌做合规对接。

### 不能承诺什么

不能直接承诺：

- 当前小票就是正式税务发票。
- 当前版本已经接入 myDATA。
- 当前版本已经满足所有希腊税务要求。
- 当前系统已经和 Viva、myPOS 或银行 POS 机联动。
- 当前版本已经支持正式复杂退款、贷项凭证和部分退货。
- 当前系统已经完成所有真实硬件兼容测试。

### 哪些属于后续定制

建议明确为后续定制：

- myDATA / 电子发票服务商对接
- Viva / myPOS / 银行 POS API 对接
- 员工账号和权限
- 复杂退款 / 部分退货
- 采购入库 / 供应商管理
- 成本价和利润报表
- 多门店 / 多仓库
- 本地打印桥 / ESC/POS / 开钱箱
- 线上支付和正式购物车

## 结论

当前项目已经具备作为 v1.0 商用演示版对外展示的完整度，但正式商用前不建议一次性盲目补齐所有合规模块。

推荐策略：

1. 先补通用商用能力，例如权限、报表、退款、备份、硬件验收。
2. 等客户确定会计师、发票服务商、POS 机品牌和实际业务流程后，再做 myDATA、正式发票和支付联动。
3. 对客户销售时，把当前版本定位为“可演示、可试运行、可定制落地”的基础系统。
